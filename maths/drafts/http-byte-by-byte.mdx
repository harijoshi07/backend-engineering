## One example for the whole lesson

In the maths app, when you answer `56` in duel `K7QM`, the Android code will look like code you've written a hundred times:

```kotlin
interface MathsApi {
    @POST("duels/{code}/answers")
    suspend fun answer(@Path("code") code: String, @Body body: AnswerBody): AnswerResult
}
data class AnswerBody(val answer: Int)

api.answer("K7QM", AnswerBody(56))
```

Retrofit turns that into a request, and OkHttp writes it to the network **as plain text**. If you've turned on `HttpLoggingInterceptor` at `BODY` level, you've seen a tidied-up version of it in Logcat ([OkHttp logging interceptor](https://github.com/square/okhttp/tree/master/okhttp-logging-interceptor)). Here are the **real bytes** with nothing tidied. I captured them by pointing `curl` at `nc` and making the invisible characters visible with `cat -v`:

```text
POST /duels/K7QM/answers HTTP/1.1^M
Host: localhost:8091^M
User-Agent: curl/8.7.1^M
Accept: */*^M
Content-Type: application/json^M
Content-Length: 13^M
^M
{"answer":56}
```

That is the whole request. Every server you'll ever build reads exactly this. Let's take it apart.

## Anatomy of a request

```text
 ┌─ request line ──────────────────────────────────────────┐
 │ POST    /duels/K7QM/answers    HTTP/1.1            \r\n │   method · target · version
 ├─ headers (name: value, one per line) ───────────────────┤
 │ Host: localhost:8091                               \r\n │   which site (required in 1.1)
 │ Content-Type: application/json                     \r\n │   what the body is
 │ Content-Length: 13                                 \r\n │   how many bytes the body is
 ├─ empty line ────────────────────────────────────────────┤
 │                                                    \r\n │   "headers are over"
 ├─ body (exactly Content-Length bytes) ───────────────────┤
 │ {"answer":56}                                           │   13 bytes, count them
 └─────────────────────────────────────────────────────────┘
```

- **`^M` is `\r`** (carriage return). HTTP/1.1 lines end with **`\r\n`**, not just `\n` ([RFC 9112 §2.1](https://www.rfc-editor.org/rfc/rfc9112#section-2.1)). Many servers also accept a bare `\n`, but you should always *send* `\r\n`.
- **The empty line is not decoration.** It's how the server knows the headers are finished. Without it, the server keeps waiting for more headers.
- **The method says what kind of action this is:**
  - `GET` means "give me something" and changes nothing on the server, e.g. `GET /duels/K7QM` to read the duel's state.
  - `POST` means "do something / create something", e.g. `POST /duels` to create a duel, or `POST /duels/K7QM/answers` to submit an answer.
- **The target** (`/duels/K7QM/answers`) is the path. On the server, the path picks *which code runs*. That's routing, coming in lesson 4.
- **`Host`** exists because one machine (one IP address) can serve thousands of sites. Cloudflare's servers answer for `example.com` *and* millions of other domains, and `Host` tells them which one you mean. In HTTP/1.1 it's mandatory; you'll see a real server reject you without it ([MDN: Host](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Host)).

## Anatomy of a response

The answer to that request, from the server you'll build, will look like this:

```text
HTTP/1.1 200 OK\r\n                       ← status line: version · status code · reason
Content-Type: application/json\r\n
Content-Length: 27\r\n
\r\n
{"correct":true,"score":5}                ← the body
```

The **status code** is the server's one-number verdict. The first digit is the category ([MDN: status codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)):

| Code | Meaning | In maths |
|---|---|---|
| `200 OK` | done, here's the result | answer checked → `{"correct":true,"score":5}` |
| `201 Created` | done, something new exists | `POST /duels` → `{"code":"K7QM"}` |
| `400 Bad Request` | your request is malformed | body is `{"answer":"fifty-six"}` |
| `404 Not Found` | that thing doesn't exist | `POST /duels/ZZZZ/answers`: no such duel |
| `409 Conflict` | valid, but the current state forbids it | answering after the 60 seconds are up |
| `500 Internal Server Error` | the **server** broke | a bug in your code |

Rule of thumb: **4xx = the client's fault, 5xx = the server's fault.** Your Android error handling already branches on this; now you're the one choosing the code.

## Where does a message end? (the lesson 1 mystery)

Bytes arrive over the network as one continuous stream. Nothing marks where one message stops, so the receiver has to be told **how many bytes the body is**. HTTP/1.1 has exactly three ways to do this ([RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112#section-6.3)):

| How | Header | How the receiver knows it's done |
|---|---|---|
| **Fixed length** | `Content-Length: 13` | reads exactly 13 bytes after the empty line |
| **Chunked** | `Transfer-Encoding: chunked` | the body arrives in sized pieces, ending with a 0-sized piece ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Transfer-Encoding)) |
| **Close** | neither | reads until the connection closes |

In lesson 1 your response had **no `Content-Length`**, so `curl` used the third rule: it kept reading until the connection closed, and Ctrl+C closed it. Mystery solved.

**Why the last option is bad:** OkHttp keeps connections open and reuses them for the next request (its connection pool). That's a big part of why your app's second API call is faster than the first. If "end of message" means "connection closed", the connection can't be reused. So real servers send `Content-Length` (or use chunked).

**What happens if the length is wrong?** I tested both cases:

```text
Server says Content-Length: 5,  sends "7 x 8 = ?"  →  curl prints "7 x 8"  and stops (exit 0)
Server says Content-Length: 50, sends "7 x 8 = ?"  →  curl prints "7 x 8 = ?" then hangs,
                                                       waiting for 41 more bytes (timed out, exit 28)
```

The receiver doesn't guess; it trusts the number. If the number is too small, the body gets cut off. If it's too big, the client hangs. That's why you'll never write `Content-Length` by hand again after today: Spring computes it for you. But now you know what breaks when it's wrong.

## Hands-on

<Steps>

1. **Be the client, against a real server.** `nc -c` sends `\r\n` line endings for you:

   ```bash
   nc -c example.com 80
   ```

   Now type these lines, pressing Enter after each one, **including the empty line at the end**:

   ```text
   GET / HTTP/1.1
   Host: example.com
   Connection: close

   ```

   You should get a real response from Cloudflare. Here's mine:

   ```text
   HTTP/1.1 200 OK
   Content-Type: text/html; charset=utf-8
   Transfer-Encoding: chunked
   Connection: close
   Server: cloudflare
   ...
   ```

   Notice `Transfer-Encoding: chunked`: this server used the second rule from the table above.

2. **Break it on purpose.** Do it again, but leave out the `Host:` line. You'll get `HTTP/1.1 400 Bad Request`, a 4xx, because the mistake was yours.

3. **See the invisible characters.** In window A:

   ```bash
   nc -l 8080 | cat -v
   ```

   In window B, send the maths answer exactly as the app will:

   ```bash
   curl -X POST http://localhost:8080/duels/K7QM/answers \
     -H 'Content-Type: application/json' -d '{"answer":56}'
   ```

   In window A, find the `^M`s, the empty line, and `Content-Length: 13`. Count the body's bytes to confirm it's 13.

4. **Be a correct server.** Press Ctrl+C in both windows. In window A run `nc -c -l 8080`, and in window B run `curl -v http://localhost:8080/question`. In window A, answer **with** a length this time:

   ```text
   HTTP/1.1 200 OK
   Content-Length: 11

   7 x 8 = ?
   ```

   (`7 x 8 = ?` is 9 bytes, and the Enter you press after it sends `\r\n`, because of `-c`, which is 2 more, so 11.) This time `curl` finishes **on its own** without Ctrl+C, because it knew exactly when to stop.

</Steps>

Until it sees the empty line, the server assumes more headers are coming. In practice it waits, and often times out. The empty line is the only "headers done" signal.
