## The example we'll take apart

In your Wordle app, to play on a real phone you typed the laptop's address into the server dialog. Something like:

```text
http://192.168.1.88:8080
       └────┬─────┘ └┬─┘
        IP address   port
```

The **IP address** picks *which machine*. The **port** picks *which program on that machine*. Both only make sense once you know what a running program is, so we start there.

## Brick 1 · Process

A **program** is a file on disk, e.g. `/usr/bin/nc`. A **process** is that program **while it's running**. The operating system (macOS here) loads it into memory, gives it a number called a **PID** (process ID), and lets it run.

You've seen this already. Logcat has a PID column, and every Android app runs as its own process. When Android kills your app in the background, that's the process ending ([Android docs: Logcat](https://developer.android.com/studio/debug/logcat)).

Two facts about processes that we'll build on:
- **One program can run as many processes.** Run the same command in two Terminal windows: same file, two processes, two PIDs.
- **A process can sit and wait.** It can be *blocked*: asleep, using no CPU, until something arrives for it. A server spends most of its life like that, and you'll watch one do it below.

> Source: *Operating Systems: Three Easy Pieces*, ch. 4 ["The Abstraction: The Process"](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf) (free; the first 3 pages are enough today).

## Brick 2 · IP address

An **IP address** is the number that identifies a machine on a network, like `192.168.1.88` ([MDN: IP address](https://developer.mozilla.org/en-US/docs/Glossary/IP_Address)). When your phone sends something to `192.168.1.88`, the Wi-Fi router delivers it to the laptop with that address.

One address is special: **`127.0.0.1`**, also called **`localhost`**, always means **"this same machine"**. Anything sent there never leaves the computer. That's why today's exercises need no network at all: everything runs on your Mac.

```text
  📱 phone ── "192.168.1.88" ──▶ Wi-Fi router ──▶ 💻 laptop (192.168.1.88)
  💻 laptop ── "127.0.0.1" ──▶ 💻 the same laptop (never leaves it)
```

So the phone uses the laptop's **network address**, and the laptop talks to itself with **localhost**.

## Brick 3 · Port

A laptop runs hundreds of processes. When bytes arrive at `192.168.1.88`, which process gets them? The **port** decides. It's a number from 0 to 65535 ([MDN: Port](https://developer.mozilla.org/en-US/docs/Glossary/Port)).

A process **listens** on a port. That means it tells the OS "anything arriving for port 8080, hand it to me". A server is a process that listens.

```text
 💻 laptop  192.168.1.88
 ┌────────────────────────────────────────────────────────┐
 │  port 8080  ◀── listened on by ──  nc        (PID 71853) │
 │  port 8000  ◀── listened on by ──  python3   (PID 73771) │
 │  port 9999  ◀── nobody                                   │
 └────────────────────────────────────────────────────────┘
   "192.168.1.88:8080"  =  this machine, that process
```

Two rules follow from this, and each one has an error message you'll see constantly as a backend engineer:

| Situation | What you see |
|---|---|
| **Nobody listens** on that port and a client tries to connect (opens a conversation with it; lesson 3 shows what that really is) | the connection is **refused**: `curl: (7) Failed to connect … Couldn't connect to server` |
| **Two programs try to listen** on the same port | the second one fails: `Address already in use` |

Some ports have conventional owners ([IANA's registry](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml)): `80` for HTTP, `443` for HTTPS, `5432` for Postgres. `8080` is just a popular choice for development servers, and it's where your Spring app will listen by default.

## Hands-on

Two small tools that come with macOS:
- **`nc`** (netcat) can listen on a port and print whatever arrives ([`man nc`](https://man.openbsd.org/nc.1)). `nc -l 8080` means "listen on port 8080".
- **`curl`** is a client: it connects to an address and makes a request ([Everything curl](https://everything.curl.dev/)).

<Steps>

1. **Start a listener and find its process.** Window A:

   ```bash
   nc -l 8080
   ```

   Window B: ask the OS "who is listening on 8080?"

   ```bash
   lsof -nP -iTCP:8080 -sTCP:LISTEN
   ```

   On my Mac it printed:

   ```text
   COMMAND   PID USER   FD   TYPE  ...  NODE NAME
   nc      71853  mac    3u  IPv4  ...   TCP *:8080 (LISTEN)
   ```

   There's the process (`nc`), its PID, and the port it's listening on.

2. **Stop it by its PID.** In window B (use *your* PID):

   ```bash
   kill 71853
   ```

   Window A's `nc` ends. Run the `lsof` command again: it prints nothing, so nobody is listening any more.

3. **Error 1: nobody listening.**

   ```bash
   curl http://localhost:8080/question
   ```

   ```text
   curl: (7) Failed to connect to localhost port 8080 after 0 ms: Couldn't connect to server
   ```

   The machine is there, but no process is at that port.

4. **Error 2: the port is taken.** For this one we use another listening program, a tiny web server built into Python. (macOS's `nc` bends this rule, so it can't show it.) Window A:

   ```bash
   python3 -m http.server 8080
   ```

   Window B, try to start a second one on the same port:

   ```bash
   python3 -m http.server 8080
   ```

   ```text
   OSError: [Errno 48] Address already in use
   ```

   Stop window A with Ctrl+C, and try window B's command again. It works now.

5. **Find your laptop's network address**, the one a phone would use:

   ```bash
   ipconfig getifaddr en0
   ```

   Mine prints `192.168.1.88`. Yours will differ.

</Steps>

<Aside type="note" title="The thing to remember">
`IP:port` names **one listening process on one machine**. Refused means no process is at that port. Address already in use means some process already is.
</Aside>

<Think id="maths-l2-ports" prompt="Your friend opens maths on their phone and gets &quot;can't connect&quot;. Using only today's three bricks, list three different reasons it could be, and the command you'd run on the laptop to check each one." revealLabel="Compare with a model answer">
1. **The server process isn't running.** Check with `lsof -nP -iTCP:8080 -sTCP:LISTEN`; empty output means start it.
2. **Wrong IP.** The phone has an old or wrong address. Check with `ipconfig getifaddr en0`, since the laptop's address can change when it rejoins the Wi-Fi.
3. **Wrong port.** The server is listening on a different port than the app uses. Same `lsof` command, without `:8080`: `lsof -nP -iTCP -sTCP:LISTEN`.

(There's a fourth reason, the server listening only on `127.0.0.1`. That brick comes in lesson 29.)
