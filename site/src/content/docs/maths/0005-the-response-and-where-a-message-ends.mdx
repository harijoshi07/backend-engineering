## Brick 1 · The HTTP response

The server's reply has the same shape as a request: a first line, headers, an empty line, an optional body ([MDN: HTTP messages](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages)). Only the first line differs. A response the maths server could send:

```text
 ┌─ status line ───────────────────────────────┐
 │ HTTP/1.1   200   OK                   \r\n  │   version · status code · reason
 ├─ headers ───────────────────────────────────┤
 │ Content-Length: 11                    \r\n  │   the body is 11 bytes
 ├─ empty line ────────────────────────────────┤
 │                                       \r\n  │
 ├─ body ──────────────────────────────────────┤
 │ 7 x 8 = ?\r\n                               │   9 + 2 = 11 bytes
 └─────────────────────────────────────────────┘
```

The **status code** is the server's verdict in one number. `200` means "it worked". The reason phrase (`OK`) is just a human-readable label for it. You've seen one other code already: `400`, when `Host` was missing. Lesson 6 covers the rest.

Retrofit reads this for you. `response.code()` is that `200`, and the body is what Moshi or Gson turns into your data class.

## Brick 2 · Where a message ends

A body can hold any bytes: JSON, HTML, an image. No byte inside it can mean "the end", because that byte might be part of the data. So HTTP solves it the only reliable way: **the sender says in advance how long the body is.** HTTP/1.1 has exactly three ways ([RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112#section-6.3)):

| How | The header | The reader stops when… |
|---|---|---|
| **Fixed length** | `Content-Length: 11` | it has read 11 bytes after the empty line |
| **Chunked** | `Transfer-Encoding: chunked` | it reads a chunk of size 0 (the body arrives in pieces, each with its size written first) |
| **Close** | neither | the server closes the connection (responses only) |

So in lesson 4, `curl` added `Content-Length: 13` so the server would know exactly where `{"answer":56}` ends. It wasn't a check that the bytes arrived. It's the *only* way the server knows when to stop reading and start answering. And `example.com` used the second way: its response said `Transfer-Encoding: chunked`.

**Why the third way is a last resort:** if "the end" means "the connection closed", every response costs a whole new connection. Clients keep connections open and reuse them for the next request. OkHttp's connection pool does this, and it's a big reason your app's second API call is faster than its first ([MDN: connection management](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x)). A request can't use it at all: the client still needs the connection to read the reply. So the standard says a request with neither header simply has no body.

**The reader trusts the number.** It doesn't guess. I tested what `curl` does with honest and dishonest lengths. The server sent the 11-byte body `7 x 8 = ?\r\n` each time and kept the connection open for 3 seconds:

| Server says | `curl` printed | Finished |
|---|---|---|
| *no length* | `7 x 8 = ?` | after 2.5 s, only when the connection closed |
| `Content-Length: 11` | `7 x 8 = ?` | **immediately**, connection "left intact" for reuse |
| `Content-Length: 5` | `7 x 8` | immediately; the other 6 bytes were dropped |
| `Content-Length: 50` | `7 x 8 = ?` | after 2.5 s, with an error: "transfer closed with 39 bytes remaining to read" |

Too small cuts the body off. Too big makes the client wait for bytes that never come. Spring will compute this number for you. Now you know what breaks when it's wrong.

## Hands-on: be the server

<Steps>

1. **No length.** Window A, a server that sends `\r\n` when you press Enter:

   ```bash
   nc -c -l 8080
   ```

   Window B (`-v` shows both sides; `127.0.0.1` skips a confusing IPv6 attempt):

   ```bash
   curl -v http://127.0.0.1:8080/question
   ```

   Window A shows `curl`'s request. Now type the response into window A: `HTTP/1.1 200 OK`, Enter, Enter again (the empty line), then `7 x 8 = ?`, Enter.

   `curl` prints your body, but **doesn't finish**. It's waiting for the connection to close, because you never said how long the body was. Press Ctrl+C in window A: now `curl` ends.

2. **With a length.** Same two commands again. This time type:

   ```text
   HTTP/1.1 200 OK
   Content-Length: 11

   7 x 8 = ?
   ```

   `curl` finishes **on its own** the moment the 11th byte arrives. In its `-v` output, the lines starting `<` are your response, and the last line says:

   ```text
   * Connection #0 to host localhost left intact
   ```

   The connection is still open, ready for another request.

3. **Lie about it.** Repeat with `Content-Length: 5` and watch the body get cut off. Then try `Content-Length: 50`: `curl` waits for 39 bytes that never come, until you press Ctrl+C.

</Steps>

<Aside type="note" title="The thing to remember">
A response is a **status line** (version, code, reason), headers, an empty line and a body. The empty line ends the headers. The body ends where **`Content-Length`** says (or at a size-0 chunk, or when the connection closes). The reader trusts that number completely.
</Aside>

The headers end at the empty line. The body can contain any bytes, so nothing inside it can mark the end. Instead the sender states the length up front, usually with `Content-Length` (or chunked, or by closing the connection, for responses only).
