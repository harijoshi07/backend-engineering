## Recall (from memory)

<Think id="maths-l6-recall-1" prompt="A response says Content-Length: 11. What happens to the connection after the 11th byte? And how does a reader find the end of a response that has no Content-Length (and isn't chunked)?" revealLabel="Check">
With `Content-Length`, the connection **stays open** ("left intact"), ready for the next request. Not closing is the whole point. Without it, the reader waits until the server **closes** the connection. It doesn't wait forever: the close is the end.
</Think>

<Think id="maths-l6-recall-2" prompt="The maths server receives your answer. Is that a request or a response? And if it has no Content-Length and isn't chunked, how big is its body?" revealLabel="Check">
A **request**: the server reads requests and writes responses. A request with neither header has **no body** (length zero). The server doesn't wait for one, because "until the connection closes" is impossible for a request: the client still needs the connection to read the reply ([RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112#section-6.3), rule 7).
</Think>

## The example for today

The maths phone app will call your server like this:

```kotlin
interface MathsApi {
    @GET("duels/{code}")
    suspend fun duel(@Path("code") code: String): Duel

    @POST("duels/{code}/answers")
    suspend fun answer(@Path("code") code: String, @Body body: AnswerBody): AnswerResult
}
data class AnswerBody(val answer: Int)
```

You know all of a request's bytes now, except three things these annotations decide: **`@GET` vs `@POST`**, the **status code** that comes back, and the **JSON** in `@Body`. One brick each.

## Brick 1 · Methods

The **method** is the first word of the request line. It tells the server what *kind* of action you want. Maths needs two ([RFC 9110 §9.3](https://www.rfc-editor.org/rfc/rfc9110#section-9.3)):

| Method | Means | Body? | In maths |
|---|---|---|---|
| **`GET`** | "give me the current state of this". **Changes nothing** on the server. | no | `GET /duels/K7QM`: read the duel and its scores |
| **`POST`** | "process this body": create something, or submit something | yes | `POST /duels`: create a duel. `POST /duels/K7QM/answers`: submit an answer |

The standard calls `GET` **safe**: a client may send it any number of times without changing anything ([RFC 9110 §9.2.1](https://www.rfc-editor.org/rfc/rfc9110#section-9.2.1)). Phones, browsers and proxies rely on that, for example to retry or cache a `GET`. So if reading a duel ever *changed* it, that would be a bug.

Method and target go together. On the server, the pair `POST /duels/K7QM/answers` picks which code runs (that's routing, lesson 9). A server that has the path but not that method answers **`405 Method Not Allowed`**.

## Brick 2 · Status codes

The status code is the server's one-number verdict, in the status line. **The first digit is the category** ([RFC 9110 §15](https://www.rfc-editor.org/rfc/rfc9110#section-15)):

| Class | Means | Whose fault |
|---|---|---|
| **2xx** | it worked | nobody's |
| **4xx** | the request is wrong: retrying the same bytes won't help | the **client's** |
| **5xx** | the server failed while handling a valid request | the **server's** |

(There's also 3xx, "look elsewhere", for redirects. Maths doesn't need it.)

The ones maths will use:

| Code | When, in maths |
|---|---|
| `200 OK` | answer checked, here's the result: `{"correct":true}` |
| `201 Created` | `POST /duels` made a new duel: `{"code":"K7QM"}` |
| `400 Bad Request` | the body is malformed: `{"answer":"fifty-six"}` |
| `404 Not Found` | no such duel: `POST /duels/ZZZZ/answers` |
| `409 Conflict` | the request is fine, but the duel's **current state** forbids it: answering after the 60 seconds |
| `500 Internal Server Error` | a bug in your code threw an exception |

In Retrofit, `response.isSuccessful()` is exactly "the code is 2xx". Until now *you* branched on these codes. From now on, your server **chooses** them, and a wrong choice misleads every client. Return `500` for a bad answer, and the app shows "server error, try later" when the player just typed nonsense.

## Brick 3 · JSON bodies

A body is bytes. **`Content-Type`** is the header that says what those bytes are ([RFC 9110 §8.3](https://www.rfc-editor.org/rfc/rfc9110#section-8.3)). For JSON, it's `application/json`. Without it, the reader has to guess, and guesses wrong. You'll see that below.

Retrofit's JSON converter (Moshi, Gson or kotlinx.serialization) does two things on each call: it turns `AnswerBody(56)` into the bytes `{"answer":56}`, and it adds `Content-Type: application/json`. On the server, Spring will do the reverse: read the header, then parse the bytes into a Kotlin data class.

So the full request your app sends to submit an answer is:

```text
POST /duels/K7QM/answers HTTP/1.1
Host: 192.168.1.88:8080
Content-Type: application/json
Content-Length: 13

{"answer":56}
```

Every line of that, you can now explain.

## Hands-on: a real JSON server

`httpbin.org` is a public test server that echoes back what you sent it, already parsed. `-i` makes `curl` show the status line and headers too.

<Steps>

1. **A correct JSON POST.**

   ```bash
   curl -i -X POST http://httpbin.org/post \
     -H 'Content-Type: application/json' -d '{"answer":56}'
   ```

   I got (some headers trimmed):

   ```text
   HTTP/1.1 200 OK
   content-length: 363
   content-type: application/json

   {
     "headers": {
       "Content-Length": "13",
       "Content-Type": "application/json",
       "Host": "httpbin.org",
       ...
     },
     "method": "POST",
     "data": "{\"answer\":56}",
     "form": {},
     "json": {
       "answer": 56
     }
   }
   ```

   Everything you've learned is in that response. The status is `200`. The response has its own `content-length` and `content-type`, because the server's JSON needs them too. And `"json": {"answer": 56}` means the server **parsed** your bytes as JSON. (Header names may be lowercase. They're case-insensitive: [RFC 9110 §5.1](https://www.rfc-editor.org/rfc/rfc9110#section-5.1).)

2. **Same bytes, no `Content-Type`.** Drop the `-H` line:

   ```bash
   curl -X POST http://httpbin.org/post -d '{"answer":56}'
   ```

   ```text
       "Content-Type": "application/x-www-form-urlencoded",
     ...
     "form": {
       "{\"answer\":56}": ""
     },
     "json": null
   ```

   `curl` labelled the body as an HTML form, the default for `-d`, and the server believed it: it parsed your JSON as a form field with a strange name, and `json` is `null`. **Same body bytes, different meaning, decided by one header.**

3. **Wrong method.** `/get` only accepts `GET`:

   ```bash
   curl -i -X POST http://httpbin.org/get
   ```

   ```text
   HTTP/1.1 405 Method Not Allowed
   ```

4. **Wrong target.**

   ```bash
   curl -i http://httpbin.org/nothing-here
   ```

   ```text
   HTTP/1.1 404 Not Found
   ```

   Both are 4xx: the server is fine, the request was wrong.

</Steps>

<Aside type="note" title="The thing to remember">
The **method** says what kind of action (`GET` reads and changes nothing; `POST` submits a body). The **status code** is the verdict (2xx worked, 4xx client's mistake, 5xx server's). **`Content-Type`** says how to read the body; for JSON it's `application/json`.
</Aside>

Reading changes nothing, so it's `GET`. Every method "sends a request", and sensitivity has nothing to do with the method.
